# MPP-Swift - Spec-Parity & Security Audit

> Generated by a multi-agent audit (62 agents): 7 paymentauth.org drafts × Swift Sources/Tests × the local
> mppx reference peer. 173 normative requirements mapped, 15 parity gaps + 18 security findings adversarially
> verified. CHID-1 (the HIGH finding) independently re-confirmed against the real code by the orchestrator.

## 1. Executive Verdict

The Swift implementation is a **strong, security-conscious port** whose core 402 machinery - challenge/credential/receipt parsing, the §5.1.2.1.1 HMAC id-binding (constant-time, rotation-aware, KAT-tested), single-use replay, expiry, RFC 9530 digest binding, and §11.6 amount/currency authorization - is implemented with dense negative tests and tracks the `mppx` peer closely across all seven drafts. The single most important theme is **identifier malleability**: one confirmed **high-severity vulnerability** lets a non-canonical base64url challenge-id pass the byte-wise HMAC gate while keying a *distinct* replay slot, breaking the single-use guarantee (a ~4× double-spend) - and it ships with **no negative test**, so it would not regress-fail. Outside that, the posture is good: the remaining security findings are low/medium hardening, spec-permissible divergences, or missing negative tests that pin already-correct behavior. Conformance is high on the wire/verification core; the genuine spec gaps are a handful of **MUSTs deferred to documented seams or scope** (low-s malleability, §10.5 session error taxonomy, Accept-Payment negotiation) plus large **deliberate scope cuts** (Tempo settled-transfer rail). Versus `mppx`, the most consequential interop breaks are self-inflicted-by-spec-correctness (Swift's spec-correct `-32043` and RFC 9530 digest vs the peer's `-32042` and bare digest) and a default-shape divergence (Tempo proof v2). Net: **fix the one high-sev bug, then converge a short list of interop/MUST items; the rest is hardening.**

## 3. Spec Gaps (confirmed MUST/SHOULD not met)

### draft-tempo-session-00

- **[MUST §5.5/§13.8] Reject high-s (canonical low-s) vouchers** - *needs code + test.*
  `MPPEVM/EthereumAddress.swift:recover` → `Secp256k1Signer.recoverPublicKey` performs no `s ≤ n/2` check; `RecoverableSignature(ethereumWire:)` only validates `v ∈ 27…30`. A malleated `s' = n−s` voucher recovers to the same signer and is accepted. No high-s negative test exists. *Shared with peer; not an exploitable double-spend (anti-replay keys on `channelId` + monotonic `cumulativeAmount`, not signature bytes), but the literal MUST is unmet.*

- **[MUST §10.5] RFC 9457 problem-type/status taxonomy** - *needs code + test.* (**high severity**)
  `MPPServer/PaymentVerifier.swift:99-103` collapses every `SessionError` into a catch-all `.settlementUnverified`, and `MPPServerMiddleware.swift:spec(for:)` maps that to a generic `verification-failed` **402**. The peer maps each failure to a distinct type/status (`session/invalid-signature` 402, `session/amount-exceeds-deposit` 402, `session/delta-too-small` 402, `session/insufficient-balance` 402, `channel-not-found`/`channel-finalized` **410**). Additionally the **`400 malformed`** case is unmet - a malformed credential returns a 402 `malformed-credential`, never 400.

- **[MUST VOUCHER] Per-challenge `minVoucherDelta` override** - *needs code + test.*
  `MPPTempoServer/SessionMethod.swift:acceptVoucher` enforces the delta but reads `minVoucherDelta` from a static `SessionMethod` init param; the peer reads a per-challenge `methodDetails.minVoucherDelta` (falling back to default). `TempoChargeRequest` does not parse `methodDetails.minVoucherDelta`, so a server cannot vary the delta per challenge. No `deltaTooSmall` negative test.

### draft-httpauth-payment-00

- **[MUST §7.4] Server-side Accept-Payment negotiation** - *needs code (low severity).*
  `MPPServerMiddleware` never reads the `Accept-Payment` request header; the peer implements full q>0 filter + descending-q + specificity ordering (`internal/AcceptPayment.ts`). **Scope note:** mpp-swift servers are single-offer-per-route by construction, so the q-filter/ordering is currently a no-op with no settlement/security impact. The "absent = accept-any" clause is only *vacuously* satisfied.

- **[SHOULD §11.12] Rate-limit** - *needs code or a doc correction (low severity).*
  No rate limiter / 429 path / rate-limit seam in `MPPServer`, `MPPProxy`, or the websocket servers (only §11.10 cache headers, a 413 body cap, and replay/credential growth bounds - none throttle rate). **Doc bug:** `SECURITY.md:33` documents "a rate-limiter seam for challenge issuance and verification" as a delivered control; it does not exist. SECURITY.md must implement it or be corrected to state rate limiting is delegated to the host.

### draft-payment-discovery-00

- **[REQUIRED §4.4.1] Offer `intent`/`method`/`amount` REQUIRED** - *needs test (and a decision on code).*
  `Sources/MPPDiscovery/PaymentInfo.swift` decodes all three via `decodeIfPresent` (lines 56-58, 61, 62); an offer missing any of them parses cleanly. **Shared divergence toward leniency** - the peer (`discovery/Discovery.ts`) also marks them `z.optional`. On the explicitly-advisory x-payment-info path (the runtime 402 is authoritative). No negative tests.

- **[SHOULD §6.3] CORS headers** - *missing, parity-matched (low severity).*
  Neither `MPPProxy`/`MPPDiscovery` emits any `Access-Control-*` header on `/openapi.json` or `/llms.txt`; the peer also omits CORS. A shared SHOULD left to the deploying app.

### draft-payment-intent-charge-00

- **[REQUIRED §5.1.1] Charge `currency` REQUIRED** - *divergent; needs a decision.*
  Tempo's charge request makes `currency` OPTIONAL while §5.1.1 marks it REQUIRED and the peer's input schema requires it.
- **[§8.1/§8.2/§8.6] Client-side amount/recipient/currency "appropriate" checks** - *partial.* Not enforced by the SDK; delegated to a user-supplied approval policy / token provider with allow-all defaults.

### Scope gaps (deliberate, not bugs)

- **Tempo settled-transfer rail (draft-tempo-charge-00):** the entire **non-zero amount** path - hash/transaction credentials, **splits**, **`fee_payer`/`fee_token`**, **pull/push mode negotiation**, `supportedModes`, RLP transaction verification, hash/receipt verification - is **deliberately out of scope** in Swift and exists only in the peer. Only the zero-amount EIP-712 proof path is implemented (byte-exact vs viem). *Scope cut, not a defect.*
- **§4.4.3 auth-before-payment (401→402):** unmodeled - N/A for this SDK (the middleware owns only the payment layer).

## 5. Security Findings (confirmed only, by severity)

### 🔴 HIGH - Challenge-id malleability → replay bypass (double-spend) `[CHID-1]`

- **Control:** single-use / unforgeable §5.1.2.1.1 challenge-id binding + §11.3 replay.
- **Spec ref:** draft-httpauth-payment-00 §5.1.2.1.1, §11.3.
- **Code site:** `Sources/MPPServer/ChallengeSigner.swift:70-79` (decode-then-MAC-check the **bytes**, never asserts canonical encoding) → `Sources/MPPCore/Base64URL.swift:44` (`Data(base64Encoded:)` ignores the final char's don't-care bits) → `Sources/MPPServer/PaymentVerifier.swift:90` (`replayStore.consume(challenge.id)` keys on the **raw string**) → `Sources/MPPServer/ReplayStore.swift` (`Set<String>`).
- **Mechanism (re-confirmed against code):** for a 32-byte HMAC (43-char id), the final base64url char has 2 don't-care bits → up to 4 trailing chars decode to the **identical MAC bytes**, so each passes `verify` (route pin/expiry/digest unchanged) yet is a **distinct replay-store key** → one captured credential drives **up to 4 settlements**.
- **Peer:** **not vulnerable** - `mppx Challenge.verify` recomputes the canonical `expectedId` and `constantTimeEqual`s the **strings**; the Swift port diverged to byte-equality.
- **Fix:** verify like the peer - compute canonical `id = Base64URL.encode(HMAC)` (the `computeID` path already exists) and constant-time compare the **string** against `challenge.id` (reject non-canonical). Or require `Base64URL.encode(decode(id)) == id`. Optionally also key the replay store on the canonical id / MAC bytes.

### 🔴 HIGH - Missing negative test for the malleability bypass `[CHID-1-test]`
Land after CHID-1: (1) `ChallengeSignerTests` mutate the final base64url char across the same-MAC group and assert `verify == false` for every variant; (2) an end-to-end `PaymentVerifierTests` case asserting a malleated credential is rejected and does not consume a second replay slot.

### 🟠 MEDIUM - Verifier accepts a credential with no `expires`; peer fails closed `[FCV-1]` (= D5)
`PaymentVerifier`/`MPPServerMiddleware` accept a no-`expires` challenge; the peer throws "missing required expires". Make `expires` mandatory at verify time or document the non-expiring mode; add the negative test.

### 🟠 MEDIUM - `StripeTokenProvider` doc claims a credential redaction that does not exist `[CRED-1]`
`Sources/MPPStripe/StripeTokenProvider.swift:65` claims the credential "redacts it in its description," but `Credential` (MPPCore) has no `CustomStringConvertible`/`CustomDebugStringConvertible`, so `String(describing:)`/`print`/`po` emit the **full SPT** (a live, single-use payment-authorizing token). Fix: give `Credential` a redacted description that masks `spt` (with an SPT-absence test), or drop the false claim and document credentials as MUST-NOT-log.

### 🟡 LOW
- **Stripe amount overflow ceiling** diverges (`Int.max` ~2⁶³ vs peer's `MAX_SAFE_INTEGER` ~2⁵³). Not exploitable (server-minted amount; Stripe caps); has a negative test.
- **`[SIG-1]` Inbound high-s not rejected on voucher/proof verify** - exact peer parity; not exploitable (identity = recovered address vs on-chain signer; anti-replay = monotonic/single-use). Already documented in SECURITY.md. Tighten only in coordination with mppx.
- **`[PROXY-TLS]` Proxy does not gate the upstream-origin scheme** - an operator-configured `http://` non-loopback `baseURL` ships the proxy's injected upstream secret in plaintext (`MPPProxy.forward`, `scheme: baseURL.scheme ?? "https"`). Cheap high-value hardening: validate origin scheme in `ProxyService.init` via `TransportSecurity.isAllowed` + negative test.
- **In-memory replay store default** does not survive restart / span instances - deployment footgun (consume itself is atomic), exact peer parity; steer production to `FileReplayStore`/shared backend + warn.

### Missing negative tests (behavior already correct; tests pin it)
`FCV-2` (missing-expires decision), `KEY-PIN` (access-key/fee-payer key not reflected), `SIG-1-test` (high-s twin), `TLS-TABLE` (loopback allow/deny incl. `localhost.attacker.com`, `::ffff:127.0.0.1`, …), `MCP-XROUTE` (cross-binding credential), `MCP-NOTIF` (gated op as notification not processed/consumed), `PROXY-CACHE` (permissive upstream Cache-Control downgraded), `DISC-CACHE` (`/openapi.json` cache header), `DIGEST-XSDK` (bare mppx digest form), `DELTA-TEST` (`deltaTooSmall`).

## 6. Remediation Order

**Phase 1 - Fix now (exploitable):**
1. **`CHID-1`** - canonicalize challenge-id at verify (reject non-canonical base64url, compare canonical string, peer-parity). The only confirmed exploitable defect (HIGH).
2. **`CHID-1-test`** - land the malleability negative tests immediately after.

**Phase 2 - Interop & MUST convergence (decide parity, then implement):**
3. **`FCV-1`/D5** - fail closed on missing `expires` at verify time + `FCV-2`.
4. **§10.5 session error taxonomy** - map `SessionError` → distinct RFC 9457 types/statuses (402/410) + the 400-malformed branch; add tests. *(MUST, high.)*
5. **`CRED-1`** - redacted `Credential` description (or correct the doc) + SPT-absence test.
6. **`SECURITY.md:33`** - correct the non-existent "rate-limiter seam" claim (or implement §11.12). Resolve **D1 `-32043`** and **D2 digest** interop divergences explicitly (document spec-correct-vs-peer, or add peer-compat acceptance).
7. **D3** - decide Tempo proof default (spec `.specChallengeId` vs peer-matching `v2Realm`); document.

**Phase 3 - MUST/low + per-challenge config:**
8. Per-challenge `minVoucherDelta` (parse `methodDetails.minVoucherDelta`) + `DELTA-TEST`.
9. Decide §7.4 Accept-Payment (document no-op vs implement) and §4.4.1 offer-REQUIRED; add tests.
10. **D4** (equal-cumulative voucher) - align to peer if interop matters.

**Phase 4 - Hardening & test-only:**
11. **`PROXY-TLS`** - gate upstream-origin scheme + test.
12. **`SIG-1`** - only if converging to literal EIP-2, coordinate with mppx; else leave documented + `SIG-1-test`.
13. Remaining missing-negative-tests (`KEY-PIN`, `TLS-TABLE`, `MCP-XROUTE`, `MCP-NOTIF`, `PROXY-CACHE`, `DISC-CACHE`, `DIGEST-XSDK`).
14. Optional: Stripe amount ceiling parity, CORS (§6.3), in-memory-replay-store production steering/warning.

*Scope items (Tempo settled-transfer rail) are intentional cuts - roadmap, not remediation.*
